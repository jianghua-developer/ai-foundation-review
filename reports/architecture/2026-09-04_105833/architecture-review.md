# AI Foundation 系列 · 总体架构评估

- 评估日期：2026-09-04
- 评估性质：**仅总体架构适配度评估**（系列级目标 → 架构映射）；不含代码评估、不含单仓内部架构评估
- 依据事实：`series-overview.md`（系列目的/设计/状态）、`fullstack-bridge` generation-architecture（两阶段重构定案）、`bridge-mcp-server` DESIGN.md（能力层定稿）、fullstack-param-protocol 协议（params.json 两区 / 派生只读）
- 结论一句话：**方向适配、边界清晰；真正的验证点是“第二组合与第一多 edge 组合”，架构张力集中在那里，而非当前单组合**

---

## 0. 评估坐标：从目标抽取的判据

系列目标（series-overview）与终态设计（DESIGN §9 场景）共同给出以下要求，作为评估“适配与否”的判据：

| 目标面 | 具体含义 | 架构应满足 |
|---|---|---|
| 生成完整业务系统 | 不只脚手架，是 AI 生成时的**约束层**；质量下限由底座抬高 | 有把“约束”下沉成机制的通道，而非仅文档劝诫 |
| 契约自动对齐 | 前后端接口靠桥对齐，AI 对照同一份契约开发 | 契约在 N≥2 成为确定性产物 + 治理闭环 |
| agent-first | 主消费者是 AI/壳；消费面是 MCP 与确定性 schema | 知识落数据、智能留壳、确定性可机器读 |
| 6 类形态 | 前后端(可含 BFF) / 纯前端全栈 / 纯后端 / 纯前端 / CLI / 其它单模板 | 单端与多端是两条不同的结构性路径，非一个万能生成器 |
| 壳无关 | 任意 MCP 壳 + 自研应用可消费 | 能力在壳外、以规范接口暴露 |
| 可演进 | 加形态/底座是常态 | 扩展尽量加数据不加代码 |
| 底座复用是资产 | 底座值得长期自述、可被零注册发现 | git + copier + 协议自述即身份 |

## 1. 目标架构主线（一句话）

**知识落底座与数据（自述/协议）、确定性交给协议+桥（数据驱动）、智能留在壳（语义/L2）、机制剥离成品（只给机制）；底座抬下限、桥治理多端契约、能力层做唯一入口，三者在“协议真源”上耦合、彼此不重复知识。**

层次拓扑：

```
壳（任意 MCP）           —— L2 语义、需求→spec、L3 人确认
能力层（薄 MCP 封装）      —— 菜单/校验/shell-out；不搬生成逻辑
    ├─ 单端链：clone → 读协议 → 指 template/ → copier     （零注册）
    └─ 多端链：shell-out 桥 cli（generate/check/内省）      （治理真源在桥）
确定性核心 / 治理           —— 桥（combos.yaml + 契约 + 漂移）；底座（template/ + copier.yml + params.json 两区）
```

判断：**主线与目标同构**。每一条系列不变量（生成≠治理、底座自描述、派生只读、桥只认 N≥2、能力层薄封装、spec 结构化）都直接对应某一目标面，没有“为目标而设、却与另一目标相悖”的机制。下面逐条给适配度。

## 2. 核心机制适配度

### 2.1 生成 ≠ 治理：单端零注册自述 ↔ “底座复用是资产”
- **适配度：高**。单端底座 = git 地址 + copier，地址即身份，注册表只是菜单不是门槛（DESIGN §4.8）。这让“加一个底座 = 加数据不加代码”在单端成立，也避免“所有模板都背注册/契约税”。
- 依赖面：自述能力系于协议（params.json）纪律——底座自持校验（CI）把它变成自检不变量，成立。
- 边界已显式：单端 params 漂移由底座自身协议 CI 兜（DESIGN §4.6），桥/能力层不介入；多端漂移由桥兜。**治理责任按“谁注册谁治理”切清**，无灰色带。

### 2.2 底座自描述 + 协议单一真源 ↔ agent-first 确定性
- **适配度：高**。原生参数字面默认/派生只读、契约模板全必填零默认 + StrictUndefined、桥/CLI 从 params.json 数据驱动选项、可执行烘焙 schema 零网络——整套是为“机器确定性消费”服务，与目标消费面一致。
- “原生字面默认 + 派生 copier 算”把自发现边界做成自检不变量（若有原生参数写 jinja 默认，桥显式告警），是低成本的强护栏。

### 2.3 契约 per-combo 手写 + 逐跳 edges + per-edge 属主 ↔ “组合少而差异大”
- **适配度：中高（在小组合矩阵内）**。不走 kind taxonomy、接线常识下沉底座 docs、edge transport 只作声明——避免了对小样本做全局抽象的过度设计税。per-edge 属主（BFF 两侧身份不同）是正确的问题建模。
- 代价：组合矩阵线性复制（契约模板 + README 元数据 + e2e per-combo 手写），且**契约不是纯数据**（每组合是手写模板）——“扩展零改动”的强主张在契约层打折为“代码零改动真、内容每组合新增”。见 §3-T4。

### 2.4 能力层薄封装 + 双路径 ↔ 壳无关、统一入口
- **适配度：高**。两条链不同被正名为“结构性正确”：单端没有治理，不值得让桥代理一整条单端链路；多端值得确定性核心 + 注册表。server 只消费桥 cli（多端）或协议直读（单端），零搬逻辑。
- spec 结构化边界（不收自然语言）+ 派生禁传 + 工具=完整意图（不拆生成子步骤）：把“智能胶水”和“确定性执行”的切点放在正确位置。

### 2.5 L1/L2/L3 选择策略 ↔ “AI 不替人定技术栈”哲学
- **适配度：高**。确定性过滤在层内（机器执行）、有界语义推荐在壳（被策展事实夹住）、L3 人确认闸门——这是系列把“智能边界”显式化的关键设计：AI 只在不违背用户个人取舍的窄带内推荐，且强制确认。与“只给机制不留成品、文档给 AI agent 读”的目标气质一致。
- selection 单一真源（底座策展、不复制进注册表）防止了“选择事实”成为第二漂移源——比把技术选型逻辑写死进桥或 server 更贴合底座演进。

### 2.6 运行形态正交（源码/可执行/烘焙）↔ MCP 消费确定性
- **适配度：中高**。frozen 的 schema/help 零网络（已实测）服务了“server/远程壳拿到确定性内省不依赖底座可达”的诉求；生成本身保留 clone（底座 template 是实时依赖）是正确取舍。运行时形态每层可配置，不绑死分发方式。

## 3. 架构张力（需在演进中盯住的点，非代码问题）

**T1 共享参数“单值广播” vs 逐端语义表达（最重要）**
多端链把共享同名参数合并成 CLI 单选项、广播到所有端（schema 去重 + 值广播）。这在双端成立（契约属主收敛值）；到 **ui-bff-api 三单元链**，会出现“同参数在不同 edge 上本可不同取值”（例：UI↔BFF 用 opaque、BFF↔真后端用 jwt）的真实诉求，而单值广播模型不表达它。这不是缺口，是**契约模型的显式简化**——但须在接入第一个 3 单元组合前定案为“共享参数全链一致是契约约束”，否则会把逐端差异悄悄压平或被迫引入逐端参数命名空间。

**T2 契约模板“再现派生”复制底座逻辑（对单一真源原则的例外）**
契约要枚举派生值（如 child_apps）而 answers 里不一定有已算好的派生 → 契约模板重新实现底座派生逻辑，注释注明“底座改派生时此处须同步”。这是“单一真源”原则自身的破口，且 check 目前只做原生参数对拍、**感知不到派生规则漂移**。当前派生只有一个、低风险；派生规则增多后会是真漂移源。建议评估“派生定义抽成协议可读规格”或“契约直接消费 copier answers 已算派生值”，让派生也单一真源化。

**T3 治理闭环是“检测自动、修复半自动”**
底座变化 → CI dispatch → 桥 check → issue 全自动；修复（改契约模板 + bump version）依赖人或 AI 在桥仓操作。对“AI 就是修复者”成立，但当组合增多、底座频繁演进时，对齐劳动线性上升。这是架构边界而非缺陷——建议保持修复在桥/人侧、不要试图自动化到“自动改契约”，把自动化停在“检测+指引”是对的。

**T4 组合矩阵线性复制成本 vs “扩展零改动”叙事**
契约 per-combo 手写意味着：加 python-vue = 复制一份契约模板 + README units 元数据 + e2e；加一个“端维度”（如再入一个前端框架）成本是全矩阵。架构对当前 2-3 组合是合理取舍，但系列应认清“生成/治理机件零改动、内容随组合线性新增”的真实曲线，避免把“代码零改动”误读为“新增零成本”。若未来组合到两位数，per-combo 手写契约的维护面会成为主成本——届时再考虑“共享契约章节按 unit 引用”机制化。

**T5 治理覆盖“下一次生成的正确性”，不含“存量生成物的升级”**
漂移/对齐闭环保证“现在跑出来的项目契约对齐当下底座”；但底座/契约演化后，**已生成项目没有升级路径**（AI 生成的存量业务代码不感知底座演进）。若目标含“AI 生成物长期可演进”，这是架构未覆盖区——应明确其归属（当前更像底座升级重新生成的替换式演进，而非原地升级机制）。不是缺陷，但要显式声明为边界。

**T6 双面登记同一底座身份（轻微双源，可接受）**
react/vue/fastapi 既在多端 combos.yaml bases、又在单端 templates.yaml 登记同一 git 身份。DESIGN 已用“共享底座同一裸名”收敛语义，但 git 地址仍物理两处。菜单语义下可接受；留意两处地址漂移（可在桥 check 或 server 启动时做一致性断言，低优先）。

## 5. 总体判断

**方向判断：适配，且成熟度与目标所处阶段匹配。** 系列架构的核心选择——把“约束/机制/协议/智能”四种东西放到不同层（底座、桥、协议、壳），并以“单一真源 + 派生只读 + 生成≠治理”作护栏——与“AI 生成完整业务系统、底座抬下限、契约自动对齐、agent-first、壳无关”的目标逐条对应，没有发现方向性错配。

**成熟度判断：当前架构把“单组合验证”做到了很好的收敛，但系列目标里最困难的部分（3 单元 per-edge 契约、能力层统一入口、跨底座治理规模）尚未被真实数据验证。** 评估结论不因“已验证部分很稳”而高估整体——真正的测试点是接下来的两个“第一”：

1. **第一个非 python-react 双端组合（python-vue）**：验证 per-combo 契约复制成本（U3）与数据驱动机件的多组合稳定性（U6）。
2. **第一个 3 单元链（ui-bff-api）**：验证 per-edge 多 edge 契约（U2）与共享参数单值模型边界（U1/T1），并暴露 T2（派生再现）是否已成为漂移源。

**演进建议（与现有待办顺序一致，不另起炉灶）：**
- 先落 python-vue（验证矩阵成本，别让它掩盖治理机件问题）；再落 ui-bff-api（一次性验证 T1/U2，据此定案“共享参数全链一致”约束）；能力层 MCP 骨架在桥成最终态后接，避免基于未定型接口建壳。
- 在 ui-bff-api 前，把 T2（契约再现派生）与 T1（共享值边界）写成明示决策记录，而不是等撞上再补——这两点会决定 3 单元链的契约模型是否成立。
- 存量项目升级（T5）与选择事实双源断言（T6）列为显式“非目标/低优先”，防止被当作隐含承诺。
